# 方案与架构（architecture）

> 目的不是"给出最优雅的设计"，而是**在真实约束下做出可解释、可回退的取舍**。
> 加载时机：技术选型、模块划分、接口设计、"用 A 还是 B"、"以后好不好扩展"。

---

## 1 什么时候真的需要做设计

| 情况 | 是否需要 |
|---|---|
| 新增一个模块 / 改接口 / 改数据结构 | ✅ 需要 |
| 存在"以后很难改"的锁定效应（存储格式、协议、引脚分配） | ✅ 需要 |
| 有多种做法且取舍不同 | ✅ 需要 |
| 改一个函数内部实现 | ❌ 不需要，直接做 |
| 用户明确要"快" | ❌ 简化，但一句话说明假设 |

**过度设计也是缺陷**：为一个 200 行的项目设计三层架构，比不设计更糟。

---

## 2 决策七步（不可跳步）

```
① 列方案（2–3 个，不凑数）
② 比较维度：正确性 / 实现成本 / 维护成本 / 扩展性 / 与现状一致性 / 可测性
③ 标明每个方案的**适用前提**
④ 结合本项目现状（RAM 大小、团队人数、交付时间）推荐
⑤ 说清被放弃方案的真实代价（不是"不好"）
⑥ 写清**什么时候需要重新评估**
⑦ 落成 ADR（.ea/DECISIONS.md）
```

### 关键：先问约束，再谈方案

设计前必须知道的四件事（不知道就问，别假设）：

1. **资源上限**：Flash / RAM / 主频 / 功耗？
2. **实时要求**：最坏响应时间？能不能阻塞？
3. **变更预期**：还会加几个外设/几种协议？
4. **维护者**：只有你，还是以后要交接？

## 4 嵌入式常见结构选择（不是"最佳实践"，是"看场景"）

| 场景 | 可选 | 取舍 |
|---|---|---|
| 中断与主循环传数据 | 全局 `volatile` 标志 / 环形缓冲 / 消息队列 | 标志最简单但会丢事件；环形缓冲零动态内存；队列灵活但常需动态内存 |
| 多任务并发 | 裸机主循环 + 状态机 / RTOS | RTOS 有调度开销与栈分配问题；裸机简单但实时性靠设计 |
| 状态处理 | `switch` 状态机 / 函数指针表 / 表驱动 | switch 直观；函数指针表易扩展但难调试；表驱动数据与逻辑分离 |
| 通信协议 | 阻塞收发 / 中断 + 缓冲 / DMA | 阻塞最简单但占 CPU；DMA 高效但复杂、易出竞态 |
| 配置存储 | 宏 / 结构体常量 / Flash 参数区 | 宏最省；Flash 参数区可现场改但需处理擦写寿命与掉电 |

**每个选择都要写"在什么条件下我会改主意"**（这正是 ADR 的价值）。

## 5 接口设计检查（比架构图更容易出错的地方）

| 检查 | 反例 | 正例 |
|---|---|---|
| 参数语义明确 | `uart_send(buf, len)` 谁是长度？ | `uart_send(const uint8_t *data, size_t len)` |
| 返回值可判定 | 返回 `void` 但可能失败 | 返回错误码或明确"不会失败" |
| 所有权清晰 | 传指针不知道谁释放 | 注释写明：调用方持有 / 函数接管 |
| 可误用性低 | 两个相邻 `int` 参数 | 用结构体或枚举 |
| 常量性 | 不该改的没加 `const` | `const uint8_t *` |
| 可测性 | 内部直接调 `HAL_` | 通过抽象层注入 |

## 6 成本估算（给量级，不给假精度）

| 项 | 怎么估 |
|---|---|
| 代码量 | 类似模块行数 × 系数（新写 ≈ 1.0，改造 ≈ 0.6） |
| 调试时间 | 通常 = 编码时间 × 1.5（嵌入式含硬件联动） |
| 风险时间 | 涉及新外设/DMA/中断优先级 → 额外 +50% |
| 回归成本 | 有无测试决定：无测试 → 改一处要手工验全部 |

输出用"人时/人天"量级，标注"粗估，误差可能 2 倍"。

## 7 ADR（精简版，写在 `.ea/DECISIONS.md`）

```markdown
## ADR-003 采用环形缓冲而非消息队列
- 日期：2026-11-19　状态：已采纳
- 背景：RAM 仅 20 KB；ISR 中不能阻塞；单生产者单消费者
- 方案：A 环形缓冲 / B 消息队列 / C DMA 直传
- 选择：A
- 理由：零动态内存、ISR 安全、吞吐满足当前 115200
- 代价：容量固定；满了要定丢弃策略（已定：丢最旧）
- 放弃 B 的原因：需要动态内存，碎片风险
- 放弃 C 的原因：当前吞吐不需要，且增加时序复杂度
- 重新评估条件：波特率 > 460800，或出现多消费者
```

模板见 `templates/adr.md`。

## 8 反模式

| 反模式 | 表现 | 后果 |
|---|---|---|
| 为模式而模式 | 小项目上三层架构 + 依赖注入 | 维护成本远超收益 |
| 虚构"最佳实践" | "业界都这么做" | 忽略本项目约束 |
| 只给一个方案 | 没有比较就说"应该这样" | 无法判断取舍 |
| 无前提的推荐 | 不说在什么条件下更好 | 换个场景就错 |
| 忽略迁移成本 | 只谈新设计多好 | 旧代码/旧数据怎么办 |
| 假精度估算 | "需要 3.7 天" | 不可信，应给量级 |

## 9 何时不该继续设计

出现以下信号，就停下来先做最小验证：

1. 讨论超过两轮但**没有一行代码或一个数据**支撑；
2. 关键约束（RAM/实时性/接口）还不知道；
3. 方案差异只在"优雅"而不在"能不能满足需求"；
4. 用户已经明确"先跑通再说"。

此时正确做法：**做一个最小原型或写一段可行性验证代码**，用事实代替争论。
