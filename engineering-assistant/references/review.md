# 代码审查与质量（review）

> 默认**只读**。审查的价值在于"每一条都能被证实或证伪"，不在于条数多。
> 加载时机：要求审查/评估质量/上线前检查/接手他人代码。

---

## 1 开工前先说清三件事

1. **范围**：审哪些文件/目录（不审的说清楚）。
2. **依据**：编译器告警？静态分析？人工规则？还是只读推断？
3. **结论上限**：本机无 clang-tidy/cppcheck/ASan → 内存与并发类结论**最高只能到"高概率风险"**，不能称"已确认"。

---

## 2 四分类（本模块的核心，必须严格区分）

| 分类 | 判定条件 | 证据要求 | 措辞 |
|---|---|---|---|
| **已确认缺陷** | 有明确触发路径，能说清"输入 X → 第 N 行 → 错误结果 Y" | 必须给 `file:line` + 触发条件 + 机制 | "这是一个缺陷：…" |
| **高概率风险** | 有明确触发条件，但是否发生取决于运行时/硬件/调用方 | 给条件 + 为什么危险 | "存在风险：当…时会…" |
| **待验证疑点** | 看起来可疑，但缺少证据（如依赖未读代码、未知库行为） | 写清"需要什么证据才能定性" | "需验证：…（验证方式：…）" |
| **一般建议** | 风格、命名、可读性、结构优化，不影响正确性 | 说明收益，不夸大 | "建议：…（不影响正确性）" |

**铁律**：
- **不符合某种风格 ≠ 有 Bug**。风格问题只能进"一般建议"。
- 拿不准 → 降级到"待验证疑点"，并给出验证方式。
- 禁止用 Critical 施压，也禁止把 Critical 说成"小问题"。

---

## 3 检查维度（逐项过，但不硬凑）

| 维度 | 要问的问题 |
|---|---|
| 逻辑正确性 | 是否实现了声明的行为？边界输入呢？ |
| 边界条件 | 0、1、最大、空、满、负数、恰好相等 |
| 异常处理 | 失败时返回什么？调用方检查了吗？错误码被吞了吗？ |
| 资源管理 | 每条路径都释放？中断里分配？句柄泄漏？ |
| 并发/中断 | 共享变量保护？临界区？ISR 与主循环竞争？ |
| 内存 | 越界、悬垂、重复释放、未初始化、对齐 |
| 整数 | 溢出、符号混用、隐式截断、移位越界 |
| 接口设计 | 参数语义清晰？错误码统一？能否误用？ |
| 模块耦合 | 全局变量滥用、循环依赖、隐式时序依赖 |
| 复杂度 | 单个函数是否过长/嵌套过深（用 `complexity.py` 排序） |
| 性能 | 有没有明显 O(n²)、忙等、冗余拷贝（**未实测只能标"待验证"**） |
| 安全性 | 输入校验、缓冲区、格式化串、敏感信息落盘 |
| 可维护性 | 命名、重复、魔法数、注释与代码不符 |
| 测试充分性 | 关键分支有无测试覆盖（结构判断，不给假百分比） |

## 4 严重程度（统一定义）

| 级别 | 标准 | 处置 |
|---|---|---|
| **Critical** | 数据损坏、安全失守、设备损坏、核心功能完全不可用 | 停止推进，先修 |
| **High** | 常见场景出错，或明确泄漏/竞态/越界 | 本轮必修 |
| **Medium** | 边界条件出错，或显著增加维护成本 | 排期修 |
| **Low** | 可读性/命名/局部冗余 | 顺手改或记录 |
| **Info** | 观察、疑问、可选优化 | 仅告知 |

定级纪律：**不确定就降一级**，并注明"可能更高，需 X 证据"。

---

## 5 误报控制：三问过关法

每条准备写下的问题，先自问：

1. **可达吗？** 这条路径在真实调用中能被走到吗？（死代码里的问题不算缺陷）
2. **已有保护吗？** 上游是否已经校验过？（重复校验不算漏洞）
3. **只是风格吗？** 若换成另一种写法行为完全一致 → 降为"一般建议"。

三问中任一答不上来 → 标"待验证疑点"。

## 6 C/C++ 快速扫描清单（10 分钟能过一遍）

```powershell
grep pattern: "\b(strcpy|strcat|sprintf|gets)\s*\("        # 不安全字符串函数
grep pattern: "\bmalloc\s*\(|\bfree\s*\("                  # 动态内存（嵌入式慎用）
grep pattern: "for\s*\([^;]*;[^;]*<=\s*"                   # <= 边界，易越界
grep pattern: "=\s*[^=]"  include: "*.c"                   # 疑似 = 与 == 混淆（需人工确认）
grep pattern: "while\s*\(\s*1\s*\)"                        # 主循环：有退出/喂狗吗
grep pattern: "(u?int(8|16|32)_t|int|long)\s+\w+\s*="      # 类型与宽度
python scripts/complexity.py --root . --top 10             # 最该读的函数
```

编译告警本身也是最便宜的审查：

```powershell
gcc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -fsyntax-only src\x.c
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Wall -Wextra -fanalyzer -c src\x.c -o build\x.o
```

## 7 能力边界（必须写进报告，不能含糊）

| 问题类型 | 本机能给到的上限 | 说明 |
|---|---|---|
| 编译期错误/告警 | **已确认** | 编译器说了算 |
| 空指针/资源泄漏（静态可判定） | 高概率（`-fanalyzer` 命中则为高置信） | 仅 ARM 侧有 analyzer |
| 内存越界/踩踏 | 待验证 | 无 ASan/Valgrind，需构造用例或硬件观察 |
| 并发/中断竞态 | 待验证或高概率 | 无 TSan，只能推理 |
| 性能瓶颈 | 待验证 | 无 profiler；只给复杂度与热点假设 |
| 协议/硬件时序 | 待验证 | 需示波器/逻辑分析仪 |

---

## 8 三种深度（按需选择，避免小任务上重流程）

| 深度 | 适用 | 做法 | 输出 |
|---|---|---|---|
| **快审** | 单文件、改动前自检 | 编译 + 四分类快速扫 | ≤5 条，只列 Critical/High |
| **标准** | 一个模块/一次提交 | 全维度过一遍 + 调用点检索 | 完整分级报告 |
| **深度** | 上线前/接手陌生项目 | 标准 + 复杂度排序 + 跨模块依赖 + 测试充分性 | 报告 + 优先处理建议 + 后续验证计划 |

---

## 9 报告（结构固定，模板见 `templates/review-report.md`）

必含：
- 审查范围与依据（含"未审"部分）
- 结论级别上限（如 V2）
- 四分类分组（无问题的组写"无"，不跳过）
- 每条：`file:line` + 现象 + 原因 + 后果 + 修复 + 验证方式
- 总体评价 + 最值得优先处理的三件事

---

## 10 审查时的禁止事项

1. 边审边改（审查模式不改代码）；
2. 只给结论不给行号；
3. 把风格偏好标成 Bug / Critical；
4. 用"可能存在问题"这类无法验证的话凑数；
5. 声称"已测试通过"却没有运行记录；
6. 把重构建议混入缺陷列表而不加区分。
