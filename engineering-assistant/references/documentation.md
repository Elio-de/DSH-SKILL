# 工程文档（documentation）

> 文档的唯一标准：**下一个人（包括三个月后的你）能据此继续工作。**
> 加载时机：写 README、接口说明、变更记录、交接文档、开发日志。

---

## 1 先定读者，再定内容

| 读者 | 想知道 | 不需要 |
|---|---|---|
| 未来的你 | 为什么这么设计、当时踩了什么坑 | 教程式基础讲解 |
| 接手的人 | 怎么编译、怎么跑、代码在哪、哪里危险 | 实现细节逐行注释 |
| 使用者 | 怎么用、参数含义、错误怎么办 | 内部架构 |
| 审阅者 | 改了什么、影响什么、验证了什么 | 无关背景 |

写之前先回答"这是给谁的"，否则会写成四不像。

---

## 2 README 结构（够用就好）

```markdown
# 项目名
一句话：<做什么，给谁用>

## 快速开始
- 环境要求：<工具链及版本，例如 arm-none-eabi-gcc 15.2.1>
- 编译：<可直接复制的命令>
- 运行/烧录：<命令或步骤>
- 预期结果：<怎么知道成功了>

## 目录结构
| 目录 | 作用 |

## 配置
| 配置项 | 位置 | 含义 | 默认值 |

## 已知限制
- <做不到什么，为什么>

## 相关文档
- [模块说明](docs/modules.md) …
```

**必须写"已知限制"**——它比功能列表更能防止误用。

## 3 接口文档：从真实签名提取，不靠记忆

```powershell
grep pattern: "^\s*(static\s+)?(inline\s+)?[A-Za-z_][\w \*]*\s+\w+\s*\([^;]*\)\s*;" include: "*.h"
```

或直接读头文件。每条接口写清：

| 字段 | 说明 |
|---|---|
| 签名 | 完整原型（`const`、指针层级都要对） |
| 作用 | 一句话 |
| 参数 | 含义、取值范围、可否为 NULL |
| 返回 | 每个返回值的含义（错误码要列全） |
| 副作用 | 是否阻塞、是否改全局状态、是否可重入 |
| 前置条件 | 必须先调用什么 |
| 示例 | 能编译的最小片段 |

**纪律**：示例代码若未编译验证，标注"示意，未编译"。

## 4 变更记录（CHANGELOG）

```markdown
## [1.2.0] - 2026-11-19
### 新增
- UART 环形缓冲，支持中断收发（`src/uart.c:120`）
### 修复
- 修复满/空判断导致的丢帧（ISSUE-007）
### 变更
- `uart_send()` 改为非阻塞，调用方需检查返回值  ← 破坏性变更
```

规则：
- 按"新增/修复/变更/移除"分类；
- **破坏性变更必须单列并写明迁移方式**；
- 每条尽量带位置或 issue 编号；
- 不写"优化了代码"这种无信息量条目。

## 5 交接文档（最容易写得空洞的一种）

必须有：
1. **当前状态**：能跑吗？哪些功能可用、哪些半成品；
2. **怎么跑起来**：从零到能编译的完整步骤（含踩过的环境坑）；
3. **关键设计**：3–5 条，附 ADR 编号；
4. **危险区**：改哪里容易炸、为什么；
5. **未完成与已知问题**：带 issue 编号；
6. **下一步建议**：优先级排序。

禁止："代码写得比较乱，自己看吧"。

---

## 6 写作规则（针对工程文档）

| 规则 | 说明 |
|---|---|
| 只写可验证的事实 | 接口名、参数、命令必须来自代码或实际执行 |
| 命令必须可复制运行 | 别写伪代码当命令 |
| 用表格替代长段落 | 参数、配置、错误码最适合表格 |
| 一个概念一个叫法 | 与 `.ea/GLOSSARY.md` 对齐 |
| 不贴大段源码 | 用 `file:line` 指路，必要时贴 ≤15 行关键片段 |
| 版本与日期 | 重要文档标注适用版本 |
| 明确"未验证" | 没测过的步骤要标出来 |

---

## 7 与知识库的分工（避免重复）

| 内容 | 放哪 |
|---|---|
| 给外部/新人看的说明 | 项目内 `README.md`、`docs/` |
| 给 AI 与自己的项目事实索引 | `.ea/PROJECT_MAP.md`、`MODULES.md` |
| 决策的历史与理由 | `.ea/DECISIONS.md` |
| 已知问题跟踪 | `.ea/ISSUES.md` |

**不要在两处维护同一份内容**——选一处，另一处放链接。

---

## 8 常见失败模式

| 失败 | 后果 | 纠正 |
|---|---|---|
| 文档描述的是"应该怎样"而非"实际怎样" | 误导后来者 | 以代码为准重写 |
| 只写 happy path | 出错时无从下手 | 补错误码与失败处理 |
| 命令缺参数/环境 | 复制即失败 | 在干净环境验证一次 |
| 更新代码不更新文档 | 文档变成谎言 | 改接口时同批更新，或标"已过期" |
| 术语漂移 | 检索不到 | 维护术语表 |
| 过度文档化 | 没人读 | 只写"不写就会出错"的部分 |
