# 冲突登记与归因示例（T04 场景）

> 场景：某库 v2.x 与 v3.x 文档对同一配置项默认值的说明不一致。
> 目的：演示"识别 → 六维归因 → 处置/保留 → 披露"的完整写法，**不演示"强行选一个"**。

## 1. 冲突本体

- 冲突编号：`X-01`
- 涉及结论：`[C-02]`（"该配置项默认值为 A"）
- A 方（v2.x 文档）：默认值为 `A`…[E-010]
- B 方（v3.x 文档）：默认值为 `B`…[E-011]
- 状态：`unresolved`

## 2. 六维归因

| 维度 | 检查结果 | 是否解释差异 |
|---|---|---|
| version | v2.8 文档写 `A`；v3.1 文档写 `B` | ✅ **主因**：主版本升级改了默认值 |
| scope | 两者均指同一配置项，无适用条件差异 | ❌ |
| timing | v2.8 发布于 2024-03；v3.1 发布于 2026-02 | ✅ 与 version 一致 |
| primaryBasis | 双方都是官方文档，但都未引用变更日志条目 | ⚠ 需补 `CHANGELOG` 佐证 |
| statisticalCaliber | 不适用（非统计数据） | — |
| cause | 最可能：v3.0 为破坏性变更，默认值随语义调整 | ✅ 待源码/变更日志确认 |

## 3. 处置

- 结论改为**条件式**：`[C-02]` → "v2.x 默认 `A`；v3.x 默认 `B`（依据各自版本官方文档）"，可信度 **低**。
- **不**判定"哪一版正确"，因为问题的实际指向是"你用的是哪个版本"。
- 给出验证建议：查 v3.0 的 `CHANGELOG` / `MIGRATION` 说明，或直接读源码默认值。
- 摘要必须提示："存在版本相关冲突 [X-01]，结论按版本分别陈述"。

## 4. 对应 `research_result.json` 片段

```json
{
  "conflicts": [{
    "id": "X-01",
    "conclusionIds": ["C-02"],
    "positionA": { "evidenceIds": ["E-010"], "statement": "v2.x 默认值为 A" },
    "positionB": { "evidenceIds": ["E-011"], "statement": "v3.x 默认值为 B" },
    "attribution": {
      "version": "v2.8 vs v3.1 主版本差异",
      "scope": "无差异",
      "timing": "2024-03 vs 2026-02",
      "primaryBasis": "双方均为官方文档，缺变更日志佐证",
      "statisticalCaliber": "不适用",
      "cause": "疑似 v3.0 破坏性变更导致默认值调整"
    },
    "status": "unresolved",
    "resolution": "按版本分别陈述，不下单一结论；建议查 CHANGELOG/源码确认",
    "impact": "影响升级迁移判断；不影响低版本使用者"
  }]
}
```

## 5. 反例（不要这样写）

- "以新版为准，v3.x 是 `B`" → 单边断言，且未解释 v2 用户为何要改。
- 不登记 `conflicts[]`，正文里悄悄写两个值 → 隐藏冲突。
- 把 `unresolved` 冲突的结论标"高可信" → 违反"不可解时可信度 ≤ 低"。
- 只在附录写冲突，摘要不提 → 未满足"摘要可见提示"。
