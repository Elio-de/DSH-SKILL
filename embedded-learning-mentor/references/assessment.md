# 评估：诊断、定级、阶段测试与错误分析

> 本文件在**首次评估、给知识定级、阶段验收、出现错误**时加载。
> 评估的目的是**定位下一步教什么**，不是打分排名。任何一次评估的结果都要能回答："接下来练什么？"

## 0 四种评估，别混用

| 类型 | 触发 | 输入 | 输出 | 写到哪 |
|---|---|---|---|---|
| **首次诊断** | 第一次系统学习；进入全新领域且档案无记录 | ≤4 题/轮（通常 2–3 题） | 起点状态（未学习/待评估/少量 L 级） | `00_个人档案/学习状态.md` |
| **单元定级** | 学完一个知识单元、做完一个实验/项目 | 解释 + 操作 + 结果 | 该单元的 L1–L4 + 证据 | `00_个人档案/学习状态.md` 台账 |
| **阶段测试** | 阶段末、里程碑验收 | 理论 + 实践任务 | 通过/未通过 + 单元等级 + 缺口清单 | `09_学习日志/`（评估记录模板） |
| **错误分析** | 出现错误，尤其同类反复出现 | 错误现象与上下文 | 错误分类、根因、训练方案、复测结果 | `06_问题与故障记录/错误台账.md` + `09_学习日志/` |

## 1 首次水平评估

### 1.1 原则

- **不假定水平，也不考试**。目的是找"从哪开始教"，不是证明他不会。
- **默认每轮 ≤4 题，通常 2–3 题**；用户答完再决定下一轮问什么。
- **七维不一次覆盖**：只测与当前目标相关的 1–2 个维度，其余随学习过程逐步补。
- 答错某题**只影响该知识点**，不否定整个领域；不确定就记 `待评估`。

### 1.2 七个维度与切入点

| 维度 | 问什么 | 看什么 |
|---|---|---|
| C/C++ 基础 | 指针/数组、结构体、位运算、编译链接 | 能否解释"变量在哪、为什么会越界" |
| 数字/模拟电路 | 电平、上拉、RC、三极管开关、电源 | 能否看懂一张最小系统原理图 |
| 单片机 | 内核、时钟、中断、外设 | 是否知道"点灯背后发生了什么" |
| 通信协议 | UART/I²C/SPI/CAN 的时序与调试 | 能否描述一次完整的收发过程 |
| PCB 设计 | 原理图→封装→布局→DRC | 是否知道去耦电容为什么靠近芯片 |
| 工程实践 | 做过什么、怎么验证、怎么排错 | 有没有"证据意识" |
| 工具与环境 | 用什么 IDE/编译链/调试器/仪器 | 是否只能靠别人帮跑 |

### 1.3 流程（5 步）

1. **读档案**：有记录就不重复问，只补空白维度。
2. **选维度**：按当前目标选 1–2 个（例：要学 STM32 → 单片机 + C 基础）。
3. **出 2–4 题（通常 3）**：至少 1 个概念题 + 1 个代码/场景题 + 1 个实践题（无法动手就换场景题）。
4. **判状态**：按 §2 的证据门槛，能定级就定级，定不了记 `待评估`。
5. **收尾三句**：强项是什么、缺口是什么、建议从哪开始；写入 `00_个人档案/学习状态.md`。

### 1.4 题目设计规则

- **一题一知识单元**，不要一题考五个点。
- 每题都有**明确判据**（答到什么算过）。
- 允许并鼓励回答"不会"——"不会"也是有信息量的结果。
- 题目来自**真实工程场景**（"这块板子上电后 LED 不亮，你先查什么"），不要背定义。
- 不出偏题、怪题、纯记忆题。

### 1.5 反模式

一次抛出十几个问题 ｜ 用难题打击自信 ｜ 把"不会"记成 L0 ｜ 只测理论不动手 ｜ 评估完不给下一步 ｜ 每轮重复问同样的问题。

## 2 知识单元的 L 级评价

### 2.1 L 级定义（以 `SKILL.md` §2 为准）

L1 了解 ｜ L2 理解 ｜ L3 应用 ｜ L4 掌握。**L0 只是"未学习/未评估"的状态标记。**
本文件只负责"用什么证据、够不够格"，不在这里另立一套定义。

### 2.2 证据类型（定级必须挂证据）

| 代号 | 证据 | 例子 |
|---|---|---|
| **E1 解释** | 口头/书面讲清概念与机制 | 能说清 GPIO 推挽与开漏的区别及适用场景 |
| **E2 操作** | 独立完成配置/编码/接线 | 不看教程配出 PB0 推挽输出 |
| **E3 结果** | 可复现的运行/测量结果 | 串口收到预期数据（V3/V4）；示波器波形（V5，用户回报） |
| **E4 迁移** | 换场景仍能做，并能说明取舍 | 换到另一型号仍能配出同样功能并解释差异 |

### 2.3 定级门槛

| 目标级 | 最低证据 | 备注 |
|---|---|---|
| L1 | E1 | 能讲清"是什么、干什么用" |
| L2 | E1 + 能定位手册对应章节（或 E2 在提示下完成） | 能讲清"为什么这样配" |
| L3 | E2 + E3 | 软件侧 V3/V4；硬件侧必须 V5（只能来自用户实测） |
| L4 | E4 + 权衡说明（代价/边界）+ 能定位该类疑难 | 能教别人、能做方案取舍 |

**四条硬规则**：

1. 不能凭"用户说自己会"直接认定 L3/L4。
2. 不能因为完成**一个简单实验**就认定整个领域掌握——等级挂在**知识单元**上，不挂在大领域上。
3. 证据不足就记 `待评估`，不写"大概 L3"。
4. 定 L3/L4 必须附**一项可复现证据**（串口日志、波形截图、测试输出、代码文件）；V5 由用户提供并注明"用户实测"。

### 2.4 单元粒度与命名

单元 = "一个可独立考核的最小主题"，例：

`STM32/GPIO`、`STM32/定时器/PWM`、`STM32/中断/NVIC`、`协议/I2C/时序`、`协议/UART/波特率`、`电源/LDO`、`PCB/去耦与地平面`、`控制/PID/参数整定`。

命名规则：`领域/子领域/知识点`，用 `/` 分层，方便台账排序与检索。

### 2.5 领域专项考核标准（示例，按需扩充）

**STM32 GPIO**

| 级 | 标准 |
|---|---|
| L1 | 了解 GPIO 的用途 |
| L2 | 理解 GPIO 输入输出模式、上下拉和工作机制 |
| L3 | 独立配置 GPIO 并完成实际控制任务 |
| L4 | 能够结合具体需求设计 GPIO 控制方案，分析异常并优化 |

**UART**

| 级 | 标准 |
|---|---|
| L1 | 知道波特率、帧格式、TX/RX 的作用 |
| L2 | 理解起始位/停止位/校验、误差来源、中断与 DMA 收发的差别 |
| L3 | 独立配置串口完成收发，能处理粘包/丢字节 |
| L4 | 能设计带帧头、长度、CRC、超时重传的通信协议并验证 |

**电源（LDO/DCDC）**

| 级 | 标准 |
|---|---|
| L1 | 知道输入输出、压差、电流能力的含义 |
| L2 | 理解纹波、效率、热耗散、去耦与布线影响 |
| L3 | 能选型并按手册搭出可用电源，测出纹波与温升 |
| L4 | 能按功耗预算、瞬态与成本做方案取舍，定位掉电/复位类疑难 |

> 其他领域按同一结构写：**用途 → 机制 → 独立完成 → 设计与排障**。

### 2.6 领域综合等级（防止以偏概全）

- 领域综合等级 = 该领域**已评估知识单元中的最低级**；没有 2 个以上已评单元就写 `样本不足`。
- 也就是说：GPIO 到 L3，不代表"STM32 掌握"；定时器还没评，综合就是"样本不足"。
- 综合等级只在 `00_个人档案/学习状态.md` 的领域总览里展示，不作为对外结论单独使用。

### 2.7 常见误判

| 误判 | 为什么错 | 正确做法 |
|---|---|---|
| "我看过教程/视频" → L2 | 输入不等于输出 | 让他讲机制或做一次 |
| "抄通了例程" → L3 | 不是独立完成 | 换引脚/换需求再做一次 |
| "一个实验成功" → 领域掌握 | 样本不足 | 记在单元上，领域写"样本不足" |
| "他以前做过类似项目" → L4 | 没有迁移证据 | 给一个新场景题 |
| "考试答对了" → L3 | 只证明 E1 | 补 E2+E3 |

## 3 阶段测试

- **时机**：阶段末、里程碑验收、或用户要求"测一下"。
- **结构**：理论 ≈40% + 实践 ≈60%；3–6 题，60–120 分钟。
- **题型**：概念解释（E1）、代码分析（E1/E2）、动手任务（E2/E3）、故障排查（E3）。
- **判级**：逐题对到知识单元，按 §2.3 门槛给级；未过的不写等级，写差距。
- **输出**：用 `templates/assessment.md` 记录；结论必须包含"下一步练什么"。
- **纪律**：可以开卷查手册——考察的是"会不会查"，不是记忆力。

### 3.4 阶段总结（用户说"总结一下/这个阶段学了什么"）

输出五块，写到 `09_学习日志/YYYY-MM-DD-阶段总结.md`，并同步 `00_个人档案/学习状态.md`：

1. **完成单元与等级变化**：哪些单元从什么状态到什么等级（带证据）。
2. **错误关闭情况**：`06_问题与故障记录/错误台账.md` 里关了几条、还开着几条、反复出现的是哪类。
3. **证据清单**：作品、实测结果、手册依据（V2–V5）。
4. **未达标项**：计划里没过的里程碑，以及原因（时间/难度/前置缺失）。
5. **下一阶段建议**：先补什么、做什么作品、预计多久。

**不要**把总结写成流水账；没有证据的"学会了"不写。

## 4 错误分析

### 4.1 七步流程

1. **识别**：先确认这是错误，不是环境问题（电压、接线、工具链）。
2. **分类**：按 §4.2 归到五类之一。
3. **直接原因**：这一行/这一步为什么错。
4. **底层漏洞**：追到知识单元（"分不清开漏与推挽"→ `STM32/GPIO/输出模式`）。
5. **训练设计**：针对该单元设计 1 个最小练习（§4.4）。
6. **复测**：换一个场景再验一次（§4.5）。
7. **更新记录**：写 `06_问题与故障记录/错误台账.md`，关闭或保持 open。

### 4.2 五类错误

| 类型 | 判据 | 典型表现 | 处理 |
|---|---|---|---|
| **偶然失误** | 同类任务平时能对，本次有明确干扰（疲劳/看错行/抄错引脚） | 一次性、不可复现 | 指出即可；同一现象 ≥2 次 → 重新分类 |
| **概念理解错误** | 解释机制时讲错，或结论对但理由错 | "开漏就是能输出高电平" | 回到机制层重讲 + 复述检验 |
| **编程方法错误** | 概念对，但写法有系统性坏习惯 | 全局变量满天飞、忙等延时、忽略返回值 | 给规范 + 代码审查清单 + 改写练习 |
| **工程设计错误** | 功能能跑，但方案在约束下不成立 | 没算功耗、没留余量、没考虑 EMC | 给约束重做方案 + 取舍说明 |
| **系统性知识漏洞** | 同一知识单元反复出错（≥2 次） | 每次都在中断优先级上翻车 | 专项补课 + 系列微练习 + 复测 |

### 4.3 根因追踪规则

- 不从"粗心"结案：**粗心是现象，不是原因**。继续问"哪一步的信息没进入你的判断？"
- 每个错误至少映射到 1 个知识单元；映射不上，说明单元粒度需要细化。
- 错误可能映射到"前置单元"（例：串口收不到，根因是时钟树没配）。

### 4.4 针对性训练设计（三选一，别只用讲）

| 方式 | 适用 | 例子 |
|---|---|---|
| **概念补课** | 概念理解错误 | 用三张对照表讲清推挽/开漏/上下拉，再让他反讲 |
| **微练习** | 编程方法错误 | 把一段阻塞代码改成中断+环形缓冲，只改这一处 |
| **复现实验** | 工程/系统性错误 | 人为制造一次过载，观察并记录复位原因寄存器 |

### 4.5 复测与关闭

- 复测必须**换场景**（换引脚、换外设、换需求），不能原题重做。
- 关闭条件：**≥2 次独立正确**（间隔 ≥1 天），且能讲清机制。
- 关闭后在 `06_问题与故障记录/错误台账.md` 标 `closed`，保留记录用于复盘。

### 4.6 错误台账与详情格式

台账**一行一条**（表格），详情单独建文件；`archive.py status` 只统计以 `| ERR-` 开头的行，不写这一行统计永远是 0。

```markdown
| ID | 首次 | 分类 | 知识单元 | 现象 | 根因 | 次数 | 状态 |
|---|---|---|---|---|---|---|---|
| ERR-001 | 2026-11-20 | 概念理解错误 | STM32/GPIO/输出模式 | 开漏点不亮 | 不知开漏只能拉低 | 2 | closed |
```

详情用 `templates/error-record.md`，文件名 `ERR-001-开漏点不亮.md`，放 `06_问题与故障记录/`。

### 4.7 反复出现时（重点）

**不能只重复提供正确答案。** 按顺序做：

1. 换表征：换一种讲法（图示/类比/波形），不要重复同一段话。
2. 拆解：把该单元再拆小（"中断优先级"拆成"分组/抢占/子优先级"）。
3. 制造对比：给两个只差一个变量的例子，让他找差异。
4. 让他教：要求用自己的话讲给"完全不懂的人"。
5. 记录并复测：进 `06_问题与故障记录/错误台账.md`，按 1/3/7 天安排**错误专项**复测（知识复习节奏见 `mentor.md` §9）。

### 4.8 反模式

把偶然失误当漏洞 ｜ 把漏洞归因于"粗心" ｜ 同一错误讲五遍原话 ｜ 只给答案不设计训练 ｜ 复测用原题 ｜ 错误记录只写"已解决"不写根因。
