# 工程实践规范（十步流程）

> 本文件在**做项目、改功能、交付**时加载。目标：把需求变成可验收的交付物，而不是"写完了"。
> **流程服务于任务，不是任务服务于流程**——简单任务不要硬套十步。

## 0 先判档，再执行

| 档 | 判据 | 走哪几步 | 典型任务 |
|---|---|---|---|
| **快线** | <2 小时、单点改动、无硬件风险 | 需求一句 → 实现 → 编译 → 报结果 | 改个延时、加个 LED、修一个笔误 |
| **标准** | 半天–3 天、涉及外设或接线 | 1-2-4-6-7-8-9 | 加一路串口协议、接一个传感器 |
| **完整** | >3 天、新板/新芯片/多人协作/涉及安全 | 全 10 步 | 从零做一块采集板 |

开场声明档位：**"这是标准档，跳过可行性分析，直接给方案。"** 用户要更快就再降一档，但要说明省掉了什么风险检查。

## 1 十步总表

| 步 | 做什么 | 产出 | 可跳过条件 |
|---|---|---|---|
| 1 需求分析 | 功能/指标/约束/明确不做 | 验收标准（可测） | 仅快线可略 |
| 2 技术可行性 | 技术/器件/工具/技能/时间 | 能做/降级做/不能做 + 理由 | 已有同类项目 |
| 3 硬件方案 | 电源树、主控、接口、外围 | 框图 + 关键参数 | 纯软件任务 |
| 4 软件架构 | 分层、模块、数据流、状态机 | 模块表 + 接口 | 快线 |
| 5 器件与资料 | 型号、手册、封装、供货 | BOM 草案 + 文档号 | 用现成开发板 |
| 6 电路与程序实现 | 原理图/代码/接线 | 可运行版本 | 无 |
| 7 编译、烧录、测试 | 编译→烧录→测量 | 证据（V3–V5） | 无 |
| 8 故障排查 | 见 `debugging.md` | 根因 + 修复 | 一次通过 |
| 9 结果验证 | 对照验收标准 + 回归 | 验证记录 | 无 |
| 10 项目文档 | README/BOM/测试/变更 | 交付包 | 快线只写 log |

## 2 需求分析（最容易被跳过，代价最大）

五问，问完写下来：

1. **做什么**：一句话功能描述。
2. **做到什么指标**：可测量（"响应 <10ms"、"误差 <1%"），不写"快""准"。
3. **什么不能做**：明确不做的功能，防止范围蔓延。
4. **约束**：供电、尺寸、成本、温度、交期。
5. **谁验收**：自己 / 老师 / 客户 / 比赛评委，标准不同。

**验收标准模板**：`在 __ 条件下，__ 能 __，误差/延迟不超过 __，用 __ 测量。`
需求变更必须记录：谁改的、为什么、影响哪些步骤。

## 3 技术可行性

| 维度 | 要回答 |
|---|---|
| 技术 | 现有技能差多少？需要先学什么？（对照 `00_个人档案/学习状态.md`） |
| 器件 | 是否有货、封装能否手焊、有无替代料 |
| 工具 | 编译链/调试器/仪器是否具备（对照 `SKILL.md` §4 环境快照） |
| 时间 | 按 `planning.md` §5 估算，是否在期限内 |

输出三种结论之一：**能做 / 降级做（砍哪个指标）/ 不能做（缺什么）**，并给理由。不要含糊地说"应该可以"。

## 4 方案设计（要点，细节见分册）

**硬件**（`hardware.md`）：先画电源树 → 算电流预算 → 定主控与接口 → 留调试口与测试点。

**软件**（`coding.md`）：分层（硬件抽象/驱动/服务/应用）→ 定数据流（谁产生、谁消费、缓冲在哪）→ 画状态机 → 保证可打桩测试。

方案要写**代价**：多一个外设就多一份功耗与调试量；能用现成模块就不要自己造。

## 5 器件与资料确认（细节见 `sources.md`）

每个器件确认五件事：**型号、封装、关键参数、手册编号、替代料**。
每个关键结论确认来源与版本。**不用"大概能用"的器件**；参数不明时不给接线方案。

## 6 编译与静态检查（本机已实测）

```powershell
# 主机侧（MinGW gcc 8.1）
gcc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -c src\x.c -o build\x.o

# 交叉编译（arm-none-eabi-gcc 15.2.1）
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Wall -Wextra -Wconversion -fanalyzer -c src\x.c -o build\x.o
arm-none-eabi-size build\firmware.elf
arm-none-eabi-nm --size-sort -S build\firmware.elf | Select-Object -Last 20
arm-none-eabi-addr2line -e build\firmware.elf -f -C 0x08000abc

# 构建系统
cmake -S . -B build -G Ninja ; cmake --build build
mingw32-make            # 本机没有 GNU make
```

**能力边界（实测，不要越界声称）**：

| 工具 | 事实 |
|---|---|
| `gcc` 8.1 | **不支持** `-fanalyzer`、无 ASan/UBSan；`cppcheck`、`clang-tidy`、`clang` 均未安装 |
| `arm-none-eabi-gcc` 15.2.1 | **支持** `-fanalyzer`（已验证能报 NULL 解引用） |
| 51 | **未检出 SDCC / Keil**：不能编译、不能声称编译通过 |
| 编译通过 | 只能证明语法与链接成立，**不能证明逻辑正确** |

要求：警告清零再谈功能；`size` 超预算先优化再烧录。

## 7 测试

- 主机侧优先：把硬件访问抽成函数指针/弱符号，用 `gcc` 在 PC 上跑逻辑。
- 用例至少覆盖：正常值、边界值、越界/非法输入、超时、重复调用、并发（若有中断）。
- Python 用 `unittest`（本机无 pytest）。
- 报告必须贴**真实运行输出**；没跑就写"未测试"，并说明卡在哪。
- 回归：改动后至少重跑受影响用例，列出跑了哪几条。

## 8 烧录与实测边界

```powershell
& "C:\Users\ouyan\AppData\Local\stm32cube\bundles\programmer\2.23.0\bin\STM32_Programmer_CLI.exe" -l
# 连接/擦除/下载/校验的具体参数以 -h 输出为准，不要凭记忆拼
```

- AI **不能**接线、不能上电、看不到波形。所有 V5 结论必须由用户执行并贴回输出。
- 没看到 `File download complete` / `Verify successful` 之类输出，**不得**写"烧录成功"。
- 用户说"烧进去了但没反应" → 按 `debugging.md` 从电源层重查，不要直接怀疑代码。

## 9 结果验证与交付

| 检查 | 要求 |
|---|---|
| 逐条对照验收标准 | 每条写"通过/未通过 + 证据（V?）" |
| 回归 | 受影响功能 + 相邻功能都跑一遍 |
| 未验证项 | 明确列出，不用"应该没问题"糊过去 |
| 风险遗留 | 写明什么条件下会出问题 |

交付物：**能编译的代码 + 接线表 + 测试记录 + 已知问题**。缺一项就说明缺哪项。

## 10 项目文档

| 文档 | 必需内容 | 放哪 |
|---|---|---|
| README | 做什么、怎么编译烧录、接线、已知问题 | `05_项目实践/<名>/` |
| BOM | 型号/封装/数量/替代料 | 同上 |
| 测试记录 | 用例/结果/证据等级 | 同上 |
| 变更记录 | 改了什么、为什么、影响 | 同上 |
| 调试日志 | 现象/假设/实验/结论 | 同上 |

## 11 证据分级（写结论必须带）

| 级 | 含义 | 可以说 | 不能说 |
|---|---|---|---|
| **V0** | 未知 | "不知道，需要确认" | — |
| **V1** | 推测 | "很可能是…，但没有证据" | "就是…" |
| **V2** | 静态可查 | "RM 里写的是…"、"代码第 88 行是…" | "所以一定能工作" |
| **V3** | 本机编译/静态分析通过 | "能编译通过" | "功能正确" |
| **V4** | 主机侧测试通过 | "在这几个用例下正确" | "板上也没问题" |
| **V5** | 目标板实测通过 | **只能引用用户提供的现象** | AI 自称"我测过了" |

写法：`结论：波特率算错了（V2，依据：RM0090 §30.4.2，实测 115200 下误差 8%）。`
**用户在自己机器上编译/烧录通过**：记 V3/V5，但必须注明"用户执行"，不是本机验证。
**禁止** V3 冒充 V4、V4 冒充 V5。

## 12 反模式

需求没写就画图 ｜ 跳过电源预算 ｜ 用"大概能用"的器件 ｜ 一次改十处再测 ｜ 编译通过就说"做完了" ｜ 只测正常路径 ｜ 文档最后补（基本不会补） ｜ 简单任务硬套十步（用户被流程拖死）。
