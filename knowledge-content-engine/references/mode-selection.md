# 模式判定（M-TECH / M-LEARN / M-HYBRID）

> 职责：把用户请求判定为一种主模式；处理用户指定、歧义、混合拆分与中途切换；输出可复述依据。
> 读取时机：S2 判定前；用户指定/改口径时；模式争议时。
> 不重复：文档类型选择见 `profiles/index.md`；简报字段见 `intake.md`。

## 1 模式定义

| 模式 | 回答的问题 | 成功标准 | 质量标准 |
|---|---|---|---|
| M-TECH | 这件事如何正确、可复现、可追溯地做成？ | 读者能照着执行并验证 | 准确 > 可追溯 > 可执行 > 完整 |
| M-LEARN | 这个特定学习者如何从现有起点真正学会？ | 学习者能理解、练习、迁移 | 准确 > 教学逻辑 > 可理解 > 练习有效 |
| M-HYBRID | 两类交付物都要 | 两件产物事实一致、各自达标 | 各自执行对应标准 |

**硬规则**：单件产物只执行一种标准；M-HYBRID 是两件单模式产物的组合，不是第三种内容模式。

## 2 信号表

| 信号 | 指向 | 分值 | 判定问句 |
|---|---|:--:|---|
| A1 交付物要被"照着执行/遵循" | M-TECH | +2 | 是否要求读者按步骤完成操作？ |
| A2 涉及参数/命令/接口/版本/规范条文/限制 | M-TECH | +2 | 是否必须给出可核对的工程细节？ |
| A3 读者为具备背景的工程师/操作者/维护者/评审者 | M-TECH | +1 | 读者是否被假定已有专业基础？ |
| A4 要求可追溯/可复现/可审计 | M-TECH | +2 | 是否要求证据、版本、复现条件？ |
| A5 交付形态为手册/说明书/规范/方案/报告 | M-TECH | +1 | 名词是否属技术文档类型？ |
| B1 目标为"学会/理解/入门/掌握/复习/转行" | M-LEARN | +2 | 是否以"学习者掌握"为成功标准？ |
| B2 读者为学习者且前置未知/差异大 | M-LEARN | +2 | 是否需先建立基础、解释术语？ |
| B3 需要原理/类比/例子/练习/测验/解析 | M-LEARN | +2 | 是否要求讲清"为什么"或安排练习？ |
| B4 要求学习路径/课程结构/循序渐进 | M-LEARN | +1 | 是否要求先后顺序与阶段？ |
| B5 需要易混点/误区/复习巩固 | M-LEARN | +1 | 是否强调"容易搞错的地方"？ |
| H1 同时要求两类产物 | M-HYBRID | 特殊 | 是否明确要两份不同用途的交付物？ |

## 3 特征抽取

1. 动作动词：写/做/整理/讲/教/学/复习/实现/排障/部署。
2. 交付名词：手册/说明书/规范/方案/报告 vs 讲义/教材/教程/路线/练习。
3. 读者描述：工程师/操作员/维护者/评审者 vs 零基础/新人/学生/转行。
4. 成功标准：能照着做通/可复现 vs 能理解/能做题/能上手。
5. 附带要求：参数、版本、命令、练习、测验、路径。
6. 显式词：技术文档模式/学习材料模式/两种都要。**混合候选词**（只作线索，不直接判 H1）："既要…也要…"、"两个版本"、"技术版+学习版"、"手册+培训材料"。
   - **必须确认"两份不同用途的交付物"才算 H1**；例如"既严谨又适合初学者"是同一份产物的双重质量要求，不是 H1（按 §10 处理）。

## 4 判定规则（按序，命中即停）

| 规则 | 条件 | 结论 |
|---|---|---|
| R0 | 用户显式指定模式 | 遵从；`decidedBy=user` |
| R0.5 | H1 命中 | M-HYBRID；先于打分，不再进入 R1–R5 |
| R1 | scoreA ≥3 且 scoreB ≤1 | M-TECH |
| R2 | scoreB ≥3 且 scoreA ≤1 | M-LEARN |
| R3 | max(score) ≥3 且 得分差 ≥2 | 取高分模式 |
| R4 | 得分差 ≤1 且 max ≥3 | 按 §5 提问或按动词判定 |
| R5 | max <3 | C1 简单级按动词判定；否则 §5 澄清；仍不明 → 默认 M-TECH |
| R6 | 保留编号（已由 R0.5 覆盖） | M-HYBRID |

## 5 歧义处置

1. 触发前提：R4/R5，且（档位 ≥C2 或用户可交互）；C1 简单级默认不提问。
2. 提问最多 1 次，合并为一句："你要的是**能照着执行的技术文档**（手册/操作/规范），还是**帮助特定读者学会的教材/讲义**（含讲解与练习）？"
3. 用户不答/跳过，或任务属 C1 简单级：
   - "执行/遵循/部署/排障/验收" → M-TECH；
   - "理解/掌握/复习/入门/练习" → M-LEARN。
4. 仍无法判定 → 默认 **M-TECH**（准确性规则更严，且可一句话切换），写 `defaultReason` 与切换方式。
5. 禁止：用提问代替可检索/可推断的信息；同一歧义重复提问。

## 6 混合拆分

| 项 | 规则 |
|---|---|
| `mode.requested` | `M-HYBRID` |
| `mode.primary` | 事实基线模式；用户未指定时 = `M-TECH` |
| `artifacts[]` | 两件：`{id, role: primary\|derived, mode, path, manifestPath, completion}` |
| 派生件路径 | `learn/main.md`，并有**独立** `learn/doc_manifest.json` 与独立 `structure/claims/exercises` 命名空间 |
| 门禁 | **每件按自身模式**：M-TECH 走 G3；M-LEARN 走 G3 事实部分 + G4；两件各自 G5，主件可 DONE + 派生件 PART |
| 一致性 | 派生件技术断言与主件逐条一致；简化标 `[简化]`；不一致 = Blocker（记录 `review.crossArtifactChecks[]`） |
| 降级 | 预算不足允许主件 DONE + 派生件 PART，`delivery.md` 逐件声明 |
| 校验 | 两份 manifest 各自 `validate_manifest.py` exit 0；主 manifest 的 artifact 必须指向存在的 `manifestPath` |

## 7 模式切换

- 记录 `log.modeChanges[]`：时间、原因、方向、已写内容处置。
- LEARN→TECH：补技术核验（G3）；TECH→LEARN：补目标/前置/练习（G4）。
- 代理自行发起的切换单次任务 ≤1 次；用户发起不限但每次记录。
- 切换后不得沿用旧模式的清单与评分。

## 8 判定记录

```json
{
  "requested": "M-TECH",
  "primary": "M-TECH",
  "decidedBy": "auto",
  "scores": { "tech": 6, "learn": 0 },
  "signals": [ { "signal": "A1", "quote": "要求能照着做通", "score": 2 } ],
  "rule": "R1",
  "defaultReason": "",
  "evidence": "命中 A1/A2/A4，scoreA=6、scoreB=0"
}
```

- `signals[].quote` 必须来自用户原话（不得转述后当引用）。
- `decidedBy ∈ {user, auto, default}`；`rule` 写 `R0/R0.5/R1–R6`。
- 记录写入 manifest `mode` 与 `review.md` 的配置快照。

## 9 判定示例

| 输入 | 命中 | 得分 | 规则 | 结果 |
|---|---|---|---|---|
| "为 STM32F407 编写串口 DMA 开发手册，工程师能照着做通" | A1/A2/A3/A4/A5 | A=8, B=0 | R1 | M-TECH / manual |
| "给零基础同事写 C 语言指针入门讲义，含练习和答案" | B1/B2/B3/B5 | A=0, B=7 | R2 | M-LEARN / lecture |
| "整理这个项目的缓存设计"（无受众/用途） | 无 | 0/0 | R5 | 提问 1 次；默认 M-TECH |
| "既要部署手册，也要新人培训材料" | H1 | — | R0.5 | M-HYBRID（primary=M-TECH） |
| "按技术文档模式写一份接口说明" | 显式 | — | R0 | M-TECH / reference |

## 10 常见误判

| 误判 | 纠正 |
|---|---|
| 出现"学习"二字就判 M-LEARN | 看成功标准：要读者执行 → A；要读者掌握 → B |
| 出现"报告"就判 M-TECH | 若目标是让非技术读者理解并练习 → B |
| 把"教程"当技术文档 | 教程以学习路径与练习为主 → B |
| 把"说明书"当学习材料 | 说明书以操作步骤与验证为主 → A |
| 用户指定后仍"自动改判" | 用户指定优先，除非用户同意并记录 |
| 混合请求先打分 | H1 必须前置（R0.5），否则会被 R4 拦截 |
| "既严谨又适合初学者"判混合 | 单件产物的质量要求 → 仍按单模式；严谨通过事实核验与断言标注，通俗通过术语解释与练习实现 |
| "既要…也要…"一律判 H1 | 只有明确要两份不同用途交付物才成立；否则按主目标判单模式 |
| 混合=一个目录一套 manifest | 两件各有独立 manifest（`learn/doc_manifest.json`），不能共用 `structure/exercises` |

## 11 测试锚点

- T-01：手册 → M-TECH；T-04：零基础讲义 → M-LEARN；T-08：混合 → M-HYBRID，连续 3 次判定一致；T-09：歧义 → ≤1 问或默认并说明。
