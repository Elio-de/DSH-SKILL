# 技术文档模式（M-TECH）写作与检查

> 职责：定义技术文档的骨架、步骤、参数/命令/接口表、代码示例、风险提示、排障、验证、方案权衡、规范条文与自检要点。
> 读取时机：S5–S6（A 模式）；S7 复核；T-01/T-02/T-03 评审。
> 不重复：证据/引用见 `evidence.md`；术语/格式见 `consistency.md`；清单见 `quality.md`。

## 1 骨架（12 类必备章节）

1. 文档信息：标题、版本、日期、适用对象、适用版本、`asOf`。
2. 目的与范围：解决什么问题；不覆盖什么。
3. 前置条件与环境：工具、权限、软硬件版本、依赖。
4. 术语与约定：术语表、缩写、标注约定。
5. 正文：按 profile 组织（概念/架构/接口/流程/步骤/参数）。
6. 参数/命令/接口表（按需）。
7. 示例：代码/配置/操作。
8. 注意事项与限制：警告/注意/提示三级。
9. 故障排查：现象→可能原因→排查→解决。
10. 验证方法：如何确认成功、边界测试、回归检查。
11. 参考与证据：来源清单 + 断言-证据映射。
12. 变更记录：版本、日期、变更点。

**规则**：不适用章节写"不适用 + 原因"，不得留空；空节 0。

**与 profile 的关系**：profile 可合并/重排章节（例如 `reference.md` 8 节、`spec.md` 6 节），但**12 类要素不可缺失**；可按 profile 合并标题，不可缺"验证/参考/变更/限制"等要素。

## 2 步骤规范（任务型内容）

每步三要素：

| 要素 | 写法 | 反例 |
|---|---|---|
| 操作 | 明确动作、工具、命令、权限 | "配置一下环境" |
| 预期结果 | 成功时看到什么（输出/状态） | "执行后观察" |
| 失败处理 | 不成功怎么办（常见错误/回退） | 省略 |

- 前置条件单列（工具/权限/备份）。
- 破坏性操作前有警告（触发条件、后果、规避）。
- 分支与判断条件明确；步骤编号稳定可引用。

## 3 参数 / 命令 / 接口表

**参数表（七列）**：输入缺失时值写 `[待提供]`，并在 `gaps[]`/`limitations[]` 登记；不得虚填默认值。

| 名称 | 含义 | 取值/默认值 | 单位 | 来源 | 适用版本 | 验证状态 |
|---|---|---|---|---|---|---|

**命令表**：用途 / 完整命令 / 参数说明 / 执行环境 / 预期输出 / 验证状态。

**接口表**：名称 / 签名或字段 / 约束 / 错误码 / 版本 / 来源。

**规则**：表中每一行可回指断言 id；无来源的行不得出现；缺单位/版本/状态 = 缺陷。

## 4 代码与示例

- 标注语言与用途；给依赖、初始化、编译/运行方式。
- 验证状态：`tested`（有运行记录）/ `compiled`（语法检查）/ `untested`（未执行，说明环境）。
- 省略部分用 `...` 并说明省略内容。
- 安全示例提示风险；不得把伪代码写成可运行代码。
- `tested` 必须记录：命令、环境、输出、退出码。

## 5 风险提示（三级）

| 级别 | 使用 | 必含 |
|---|---|---|
| 警告 | 可能导致数据丢失/设备损坏/安全风险 | 触发条件、后果、规避 |
| 注意 | 可能导致失败/返工 | 条件、影响、建议 |
| 提示 | 体验/效率建议 | 说明 |

- 不可逆操作必须在步骤前出现。
- 禁止"尽量小心"式模糊措辞。
- 风险内容无来源时标 `[未验证]`。

## 6 故障排查

| 现象 | 可能原因 | 排查步骤 | 解决方式 |
|---|---|---|---|

- 未确认原因标 `unverified`；不得编造故障机理。
- 区分"环境问题/配置问题/代码问题/版本问题"。

## 7 验证方法

- 如何确认操作成功（检查点、命令输出、状态）。
- 边界条件测试（最小/最大/异常输入）。
- 回归检查（升级/迁移后）。
- 无法执行验证时，给出可复现验证步骤并标 `untested`。

## 8 技术方案（design）

输出结构：

1. 背景与目标。
2. 约束与假设。
3. 候选方案（≥2）。
4. 评估维度与权重/依据。
5. 逐方案分析（事实 + 推论）。
6. 结论与理由。
7. 风险与回退。
8. 验证与落地步骤。

**规则**：权衡矩阵 ≥3 维度；结论区分 `[事实]/[推论]/[建议]`；建议不得写成事实。

## 9 开发规范（spec）

- 条文四级动词：**必须 / 应该 / 可以 / 禁止**。
- 每条含：判定条件、适用范围、例外、违反后果（如适用）。
- 禁止"合理使用""尽量规范"等不可判定表述。
- 每条可被第三人判定"遵守/违反"。

## 10 断言标注（与 evidence.md 一致）

- 行内：五类核心 `[事实]`、`[推论]`、`[建议]`、`[意见]`、`[未验证]` + 状态标记 `[待提供]`、`[示例]`；或统一用 `[CL-##]` 指向台账。
- 覆盖率门槛：关键断言（参数/命令/接口/版本/安全/限制）100% 显式标注；非关键断言 ≥90%，抽 20 条复核。
- `[简化]`：技术降维表达，附简化边界。
- `[类比]`：类比，附不成立处。
- `[转引]`：非一手，注明原始出处。
- `（未确定）`：附核实途径。

**规则**：`[意见]` 不得进入规范条文、安全提示、验收条件；`[事实]` 必须有来源。`[CL-##]` 只表示可追溯，**不能替代**类别标注（关键断言必须可见类别或明确判句）。

**破坏性/不可逆操作清单**（命中即必须有前置警告）：烧写/擦除固件、覆盖配置、删除数据、格式化、量产校准、OTA 升级、修改安全策略、不可回滚的迁移。警告须含触发条件、后果、规避/回退。

## 11 可复现信息

涉及部署/构建/调参/评测时记录：硬件（型号/规格）、软件（版本/构建号）、工具链、OS、依赖清单、关键参数、步骤、预期结果。缺失项标 `unknown` 并说明对复现的影响。

## 12 A 模式自检要点（写作时）

| # | 检查 | 判据 |
|---|---|---|
| 1 | 必备章节 | 12 类齐全或"不适用"有原因 |
| 2 | 空节 | 0 |
| 3 | 步骤三要素 | 100% |
| 4 | 参数表 | 七列齐全、逐行有来源/版本/状态 |
| 5 | 命令/接口表 | 字段齐全 |
| 6 | 代码状态 | 100% 标注；tested 有记录 |
| 7 | 风险提示 | 三级、条件/后果/规避 |
| 8 | 破坏性操作 | 前置警告 |
| 9 | 排障表 | 现象/原因/处理；未确认标注 |
| 10 | 验证方法 | ≥1 个可执行 |
| 11 | 方案权衡 | ≥3 维度、风险与回退 |
| 12 | 规范条文 | 四级动词、可判定 |
| 13 | 版本声明 | asOf + versionRange |
| 14 | 引用完整性 | 断链 0 |
| 15 | 断言标注 | 五类可判定 |
| 16 | 不确定性 | 未验证项可见 |
| 17 | 可复现信息 | 环境/依赖/版本/步骤（适用时） |

## 13 常见缺陷

| 缺陷 | 修复 |
|---|---|
| 参数无单位/版本 | 补七列表格字段 |
| 代码"已验证"无记录 | 改 `untested` 或补运行记录 |
| 步骤缺预期结果 | 补"成功看到什么" |
| 风险藏在正文 | 提为警告块并前置 |
| 版本未声明 | 补 `asOf`/`versionRange` |
| 方案只列结论 | 补候选、维度、依据、回退 |
| 规范"合理即可" | 改四级动词 + 判定条件 |
| 引用断链 | 补台账或删除引用 |

## 14 与学习材料的边界

- 技术文档可以"压缩、条目化"；不得要求循序渐进。
- 学习材料中的类比与练习不属于技术文档；文档中不得把类比当操作依据。
- 混合请求拆两件产物，见 `mode-selection.md` 与 `delivery.md`。
